# Kali SSH 조건별 실효 출력 대조 — 2026-10-29

사용자가 현재 연결된 Kali Tera Term에서 실행해 전달한 결과를 대조했다. 에이전트가 게스트 명령을 직접 실행한 결과가 아니다. 원본 설정 전체 대신 제공된 5개 값의 검토 사본을 프로젝트 Linux 스캐너에 각각 입력했다. 현재 코드 f4ec647에서 4조건 × 5항목 = 20개 판정 일치(assertion 통과)를 확인했다. [구조화 근거](evidence.json)의 해시는 정규화한 검토 사본의 해시이며 게스트 원본 파일의 무결성 증명이 아니다.

문법 검사는 사용자 제공 출력에서 통과했다. root/nobody 각각에 대해 loopback과 현재 SSH 접속원, 숫자 주소 기반 host 조건을 지정한 네 경우에 아래 값이 동일했다. 외부 전달용 문서에는 실제 접속 IP를 기록하지 않았다.

| 항목 | 네 조건의 값 | 현재 모듈 판정 |
| --- | --- | --- |
| PermitRootLogin | yes | warning |
| PasswordAuthentication | yes | warning |
| PermitEmptyPasswords | no | pass |
| PubkeyAuthentication | yes | pass |
| MaxAuthTries | 6 | warning (모듈의 1~4 기준 초과) |

이는 선택한 조건에서 해당 5개 값이 같다는 의미다. nobody에 대한 -T 출력은 nobody 로그인이 가능하다는 증거가 아니다. PubkeyAuthentication yes도 실제 키 배포·키 로그인 성공을 증명하지 않는다. 경고는 현재 모듈의 검토 기준이며 실제 침해 판정이 아니다.

이전 명령의 zsh 분리 문제로 lport가 비어 실패했으나 명시적인 sh 실행으로 수정한 명령에서는 정상 출력이 나왔다. 이 실패는 SSH 서비스 설정 오류나 변경이 아니었다.

## 남은 범위

- 서비스 실행 표기는 `/usr/sbin/sshd -D $SSHD_OPTS`, `/etc/default/ssh`의 `SSHD_OPTS`는 공백임을 사용자 제공 출력으로 확인했다. 표시된 범위에 별도 -f/-o는 없다. 실행 프로세스에 전달된 최종 환경·서비스 override 전체를 독립 확인한 것은 아니다.
- 기본 설정에 활성 Include 한 줄(`/etc/ssh/sshd_config.d/*.conf`)이 있으며 전달된 검색 결과에 활성 Match는 없었다. 후속 사용자 출력에서 대상 .conf 파일 1개와 활성 항목 이름 AuthorizedKeysCommand·AuthorizedKeysCommandUser를 확인했다. 설정값·프로그램 경로·실행 사용자·소유권/권한·조회 결과는 아직 받지 않았다.
- 원본 Include/Match·포함 파일 및 실제 필요한 그룹/호스트/주소 조건의 전체 범위 확인
- 별도 격리 환경에서 실제 로그인 성공/거절과 복구 경로 확인
- 이번 조건별 자료의 운영 회원 저장·재검증은 아직 미실행

설정 변경·키 등록·서비스 재시작은 하지 않았다. Linux 조건별 검증은 부분 확인으로 유지하며 2단계 전체 완료로 바꾸지 않는다.


## 포함 파일의 공개 키 조회 명령

사용자 제공 목록에는 AuthorizedKeysCommand와 AuthorizedKeysCommandUser가 있다. 이 선언 자체를 취약점으로 판정하지 않는다. OpenSSH 공식 문서상 공개 키 조회 프로그램은 절대 경로·root 소유·그룹/타인 쓰기 금지 요건이 있고 별도 전용 실행 계정을 권장한다. 이 프로그램을 임의 실행하거나 수정하지 않았다. 기본 모듈의 5개 판정은 프로그램의 신뢰·공개 키 조회 정책·실제 인증 성공을 검증하지 않는다. 해당 경로는 별도 미검증으로 기록한다.

근거: https://man.openbsd.org/sshd_config#AuthorizedKeysCommand 및 https://man.openbsd.org/sshd_config#AuthorizedKeysCommandUser .

사용자 후속 sshd -T 출력: `AuthorizedKeysCommand /usr/bin/userdbctl ssh-authorized-keys %u`, `AuthorizedKeysCommandUser root`. systemd userdbctl의 공개 키 조회 기능에 해당한다. root 실행 사실은 확인됐지만 바이너리 무결성·파일/경로 쓰기 권한·조회 정책은 미검증이다. root라는 이유만으로 침해나 취약점 확정 판정을 내리지 않는다. 임의로 프로그램을 실행하거나 전용 계정으로 변경하지 않았다.

공식 대조 추가: systemd userdbctl 매뉴얼의 Integration with SSH 예시가 사용자의 두 줄(ssh-authorized-keys %u, 실행 사용자 root)과 정확히 일치한다. 따라서 이 root 실행 설정 자체를 비표준 취약 구성으로 표시하지 않는다. 이는 현재 VM 바이너리·권한·키 조회 정책의 정상성을 보증하는 것은 아니다. 근거: https://www.freedesktop.org/software/systemd/man/latest/userdbctl.html#Integration%20with%20SSH .

## 실행 파일 경로 권한·패키지 소유 대조

후속 사용자 제공 namei 출력: `/`, `/usr`, `/usr/bin`은 root:root 0755이고 `/usr/bin/userdbctl`도 root:root 0755였다. 기본 UNIX 모드 기준 그룹/기타 쓰기가 없다. dpkg-query는 `systemd-userdbd: /usr/bin/userdbctl`을 반환했다. 따라서 OpenSSH의 실행 파일 root 소유·그룹/타인 쓰기 금지 요건은 제공된 기본 모드 범위에서 충족한다. 설정도 systemd 공식 SSH 연동 예시와 같다.

이 확인은 패키지 파일 내용 무결성·확장 ACL·조회 원천의 신뢰·실제 인증 성공/거절을 증명하지 않는다. 등록된 패키지 이름만으로 바이너리가 변조되지 않았다고 단정하지 않는다. 기존 5항목 경고 3개는 그대로이며, 이번 경로 권한 충족을 전체 SSH 안전 판정으로 합치지 않는다.

## 로컬 패키지 검증 결과

사용자는 직전 안내한 `dpkg --verify systemd-userdbd` 실행에 대해 불일치 메시지 없음과 `verify_exit=0`을 전달했다. 프롬프트 일부가 깨져 있어 정확한 명령 실행을 독립 확인한 것은 아니며 사용자 보고로 분류한다. 보고된 명령을 실행했다는 조건에서, 로컬 dpkg 검증 정보와 비교해 불일치가 보고되지 않은 결과다. 신뢰 저장소 원본과의 독립 무결성 검증이나 로컬 검증 DB의 신뢰 보장, 실제 인증 시험과 구분한다.

이번 출력 대조 범위는 정리 완료이며 설정 변경은 없다. Linux 전체 완료가 아닌 구성/선택 조건/기본 파일 권한/로컬 패키지 검증에 대한 부분 확인이다. 외부 키 조회와 실제 로그인 성공/거절, 운영 회원의 이번 자료 저장·재검증은 남아 있다.

## 실제 시험 첫 실행: 실패, 완료 아님

사용자 제공 첫 시험 출력은 allowed_key 실패(clientExit 255), 나머지 네 거절 사례는 스크립트상 PASS였고 CLEANUP_OK가 출력됐다. 정상 로그인 양성 대조가 실패했으므로 전체 인증 검증은 실패/미완료다. 거절 네 개도 단독으로 인증 정책 정확성을 입증한 결과로 계산하지 않는다.

초기 하네스는 임시 authorized_keys를 /tmp 아래에 뒀다. OpenSSH safe_path는 상위 디렉터리도 그룹/기타 쓰기 권한을 확인하므로 통상 world-writable /tmp는 StrictModes 거절을 유발할 수 있다. 이것은 시험 코드의 설계 결함이며, 초기 서버 로그를 보존하지 않아 이번 실제 실패의 원인으로 확정하지는 않는다. 다른 원인도 배제하지 않는다. v2는 /run 및 상위 경로의 root 소유/쓰기 금지를 확인해 사용하고 StrictModes는 유지한다. 비밀 원문 없는 원인 코드와 정상 대조 실패 시 INCONCLUSIVE 처리를 추가했다. 수정본은 Python 문법 검사만 통과했으며 Kali 재실행 결과는 아직 없다. 초기 스크립트 전달 서버는 종료했다.

근거: https://github.com/openssh/openssh-portable/blob/master/misc.c 의 safe_path 함수.

## v3 경로 검증 계획과 표시 정책 — 실제 실행 대기

일반 키 파일 외에 다른 위치·안전한 링크·없는 파일·시험 파일의 과도한 쓰기 권한·시험 상위 폴더의 쓰기 권한·불안전한 대상을 가리키는 링크를 포함해 총 11개 시나리오를 준비했다. 작업 기반 경로는 후보의 실제 소유권/쓰기 권한/읽기 전용 상태/생성 성공을 확인해 선택한다. 특정 경로명만으로 안전/위험을 단정하지 않는다.

사용자 요청에 따라 경로 지정 자체는 `info` 참고 안내로만 표시한다. 실제 거절과 확정된 원인은 별도로 설명하며, 로그/파일 상태의 근거 없이 경로 때문에 거절됐다고 하지 않는다. 계정 차단·키 불일치는 경로 이동으로 해결하라고 안내하지 않는다. 시험 결과 FAIL과 보안 경고를 구분한다.

독립 Python 보고 계약 검사 5개는 통과했지만 실제 Kali 인증 11개 통과를 뜻하지 않는다. v3는 실행 대기이며 이전 정상 키 실패는 미해결 상태로 유지한다. 확장 ACL·MAC 정책·현재 SSH 원본 정책 전체는 미검사다. 현재 사이트의 정적 5항목 모듈에 실제 경로 검사 기능이 추가된 것은 아니고, 이 변경은 별도 검증 도구와 준비 문서에 적용한 것이다.

## v3 실제 실행 결과 및 남은 1개

[사용자 제공 구조화 출력](auth-run-v3.json)은 정상 양성 대조 성공, 총 11개 중 10개 PASS·missing_key_file 1개 FAIL이다. 정상 경로/다른 위치/안전한 링크의 성공과 경로/계정/정책별 거절 결과를 확인했다. 해시 확인과 정리 성공은 사용자 보고다. 원격 정책 전체 검증이나 사이트가 자동 실행한 검사는 아니다.

파일 없음 사례는 실제 파일 없음과 exit 255를 관찰했으나 특정 로그 문구 조건을 충족하지 않았다. 정확한 원인은 미확정이며 이번 결과를 통과로 바꾸지 않는다. v4는 동일 서버·키·경로에서 공개 키 파일이 없을 때 거절되고 임시 파일을 같은 경로에 복원하면 성공하는 짝지은 시험을 추가했다. 실효 파일 경로/외부 조회 비활성 조건도 확인한다. 보고 계약 7개는 통과했지만 실제 VM 재실행 전이다. 경로 안내는 info이며 파일 부재를 보안 취약점 자체로 표시하지 않는다.

## 최종 v4 격리 인증 시험 — 11/11 통과

2026-10-29 사용자 제공 [v4 구조화 결과](auth-run-v4.json)를 독립 확인했다. 보고된 다운로드 해시가 준비한 v4 해시와 같고 SHA 검사 OK·CLEANUP_OK가 있다. 정상 키/다른 키 위치/안전한 링크는 각각 exit 0, 나머지 거절 8개는 exit 255 및 개별 기대 근거로 모두 PASS다. 정상 양성 대조도 성공했다. missing_key_file은 파일 없음·인증 거절 후 같은 서버/키/경로에서 시험 공개 키 파일만 복원했을 때 exit 0/Accepted publickey가 확인돼 짝지은 시험을 통과했다. 경로 지정 안내는 11개 모두 info였다.

**준비한 localhost 격리 시험 행렬 11개는 완료**로 갱신한다. v1 실패·v3 10/11 이력은 보존한다. 실제 명령 실행 주체는 사용자이며, 에이전트는 보고된 클라이언트 결과·서버 로그 기반 고정 코드·메타데이터·복원 대조의 일관성을 확인했다. 로그 원문을 별도로 받거나 모든 프로세스를 직접 관찰한 것은 아니다. 임시 Windows 전달 서버도 에이전트가 종료했다.

현재 운영 22번/외부 userdb 키 조회·실제 비밀번호 제출·확장 ACL·SELinux/AppArmor·모든 사용자/네트워크 조건을 완료로 확대하지 않는다. 이번 시험 기능이 사이트에 자동 SSH 접속 기능으로 제공된 것도 아니다. 운영 회원의 이번 자료 저장/재검증과 DB 장기 안정성/복구·외부 Mac/Android 검증이 남아 **2단계 전체는 진행 중**이다.
