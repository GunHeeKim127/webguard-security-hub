# IP·계정 블랙리스트와 관리자 해제

2026-10-27 로컬 구현/검증 기준. **운영 migration·배포는 아직 적용하지 않았다.** 기존 IP만 있던 상태에서 계정 정책을 추가한 변경이다.

## 차단 기준

- IP: 신뢰 접속 주소 기준, 정해진 위험 URL 패턴 감지 시 5분 임시 차단. 임시 차단 5회 이후 6번째 위반에 영구 등록. 차단 중 반복/동시 요청은 추가 누적하지 않는다.
- 계정: 서버 DB에서 유효한 세션으로 확인된 사용자에게만 해당 새 위반을 연결한다. **아이디/이메일/사용자 ID를 요청에 적었다는 이유로 타인 계정을 차단하지 않는다.** 위조·만료·중복 세션 쿠키는 인증 근거가 아니다.
- 계정은 자체 누적 6번째 위반에 블랙리스트 등록하고 기존 세션을 폐기한다. IP와 계정 누적은 독립적이다. 익명 방문자의 과거 IP 위반을 뒤늦게 로그인한 계정의 위반으로 옮기지 않는다.
- 차단 계정은 유효 비밀번호를 입력해도 같은 일반 인증 실패 응답을 받는다. 모든 보호된 요청의 세션 조회도 계정 차단을 확인하므로 이미 진행 중이던 로그인 경합만으로 보호 기능에 다시 접근하지 못한다.
- IP 기록은 공격자 실명/위치/원래 주소를 증명하지 않는다. VPN·프록시·공유 NAT의 한계가 있다. 이 허브의 정의된 URL 패턴만 보호하며 모든 공격 탐지나 외부 사이트 WAF가 아니다.

## PostgreSQL

| 테이블 | 용도 | migration |
|---|---|---|
| `public.ip_blocks` | IP·위반 횟수·임시 만료·영구 차단 | 기존 PG 005 / 관리형 001 |
| `public.account_blocks` | 계정 ID·위반 횟수·영구 차단·사유·최초/최근 시각 | **신규 PG 011 / 관리형 007** |
| `public.events` | 차단/관리자 해제 감사 | 기존 테이블 재사용 |

기존 적용 migration은 편집하지 않았다. 운영 변경 전 승인된 migration 프로필에서 새 migration을 적용하고, 일반 PG는 최신 `scripts/grant-runtime.ts`로 runtime 권한을 적용해야 한다. readiness는 계정 테이블/쓰기 권한이 없으면 준비 완료로 처리하지 않는다. **이 새 코드를 migration 없이 먼저 배포하면 인증/보호가 실패할 수 있으므로 운영 적용 순서 검토가 필요하다.** 제공자 관리 자격의 실제 ACL 검증은 여전히 별도 잔여 작업이다.

## 관리자 관리

관리자 로그인 → 웹 진단 작전실(`/?view=web`) → 위험 접근/IP 차단 및 계정 블랙리스트 패널. 최근 50개 위반 기록에서 해당 해제 버튼을 사용한다. 일반 고객에게 IP/타 계정 차단 목록을 내보내지 않는다.

- `/api/admin/ip-blocks`: 관리자만 IP의 누적·영구/임시 차단을 초기화한다.
- `/api/admin/account-blocks`: 관리자만 계정 누적·영구 차단을 초기화하고 세션을 폐기한다. **해제 후 새 로그인 필요**. IP 차단은 별도로 남는다. 일반 로그인 요청 한도도 독립적으로 적용된다.
- 서버가 현재 관리자 역할/세션·Origin·본문 필드·대상 형식·10회/분 관리자별 한도를 확인한다. 클라이언트의 actorId/role 주장은 허용하지 않는다.
- 해제·세션 폐기·감사 입력은 하나의 SQL 문으로 처리한다. 감사 실패 시 해제를 롤백한다. 감사에는 관리자 계정 ID·DB 생성 시각·대상 IP/계정의 SHA-256 식별자를 기록한다. 비밀번호·원문 세션은 기록하지 않는다.
- 차단 행을 삭제하지 않고 `manual_reset`으로 남긴다. 관리자 본인의 IP/계정이 차단된 경우 웹 차단 우회 예외를 만들지 않았다. 다른 승인된 관리자 접속이나 제한된 로컬 migration 자격의 `scripts/unblock-ip.ts`, `scripts/unblock-account.ts` 복구 경로가 필요하다. 로컬 계정 복구는 별도 local 감사 이벤트를 남긴다. 운영 복구 명령은 이번에 실행하지 않았다.

## 검증과 한계

실제 loopback 임시 PostgreSQL과 HTTP API에서 익명/회원/교차 출처/actor 위조 해제 거절, IP 5회/6번째 정책, 계정 위조·만료·중복 쿠키 거절, 동시 위반 비누적, 계정 6번째 차단·세션 폐기·재로그인 거절, 관리자 감사 쓰기 실패 롤백, 해제 후 새 로그인 회복을 교차 확인했다. 일반 PG·관리형 migration을 별도 임시 스키마에서 검증했다.

로컬 브라우저의 별도 테스트 관리자 계정으로 IP/계정 해제 버튼을 눌러 성공과 목록 갱신도 확인했다. 정상 사용자/운영 차단을 해제한 것은 아니다. 이미 인증돼 실행 중인 모든 작업의 강제 취소, 실제 공격자 신원 확인, 전체 이상 행위 탐지, 관리형 DB 키 탈취 이후의 감사 무결성은 보장하지 않는다.

### 2026-10-27 후속: 마스킹 관리 참조

일반 PG 012 / 관리형 008도 필요하다. 각 차단 행에 유일한 management_id를 추가하고 readiness에서 확인한다. 목록에는 마스킹 IP/이메일과 blockId만 전달한다. 두 관리 API 모두 POST `{action:"release",blockId}` 형식을 사용하며 원문 IP/userId 입력은 거절한다. 서버가 참조를 실제 대상으로 해석하고 같은 참조에 대해 원자적으로 해제한다. 상세 근거는 검토 보고서 17~19절과 DATA_EXPOSURE_BOUNDARY.md를 참조한다.

2026-10-27 운영 후속: 사용자 요청으로 관리형 007·008을 실제 적용했다. 007의 REVOKE는 제공자 금지 명령이라 적용 전 제외했으며, 적용 후 account_blocks의 PUBLIC 테이블 권한이 없음을 조회했다. 일반 PG 011의 REVOKE는 유지한다. 제공자 자격의 권한 분리는 별도 한계다. 검토 보고서 20절 참조.
