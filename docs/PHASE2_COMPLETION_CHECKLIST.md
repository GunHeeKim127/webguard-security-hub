# 2단계 잔여 검증의 절차와 완료 기준

> **최신 인계: 2026-10-30.** [완료 범위·다른 PC의 남은 작업](PROGRESS_HANDOFF_2026-10-30.md)을 먼저 읽으세요. 아래 과거의 Android 미실행/다음 우선 작업·172개 회귀 표시는 당시 기록입니다. 현재 실제 APK·Android 가상 브라우저·모바일 더미 사용자 흐름은 확인됐고, 전체 회귀는 177 통과·실패 0·건너뜀 1입니다.


> **2026-10-30 모바일 더미 후속:** IPA/AAB/APKS/XAPK 합성 취약·보완 8개를 PC 사용자 순서로 검사·저장·재검증했고 형식별 JSON 다운로드와 DB 대조를 통과했다. 잘못된 입력 2개는 거부·저장 차단. IPA 경고 1→0·미검사 3 유지, 나머지 형식은 미검사 6 유지. 실제 iOS 기기/앱 실행이나 AAB protobuf·중첩 앱 검증을 대체하지 않는다. [검증 내역](validation/2026-10-30-mobile-dummy/README.md). 2단계 전체 진행 중.


> **2026-10-30 Android 후속:** 이 PC의 실제 프로젝트 APK 2개를 Android SDK AAPT2와 사이트 파서로 대조해 명시 설정/권한 수가 일치했다. 일반 회원의 실제 APK A 읽기 동의·검사·저장·조회·JSON 다운로드, 같은 자산 재검증과 다른 계정 거절을 격리 DB에서 확인했다. Emulator 37.2.13/Platform-Tools 37.0.1 업데이트 후 기존 Android 11 부팅·WHPX 가용을 확인했다. Android 16 가상기기·Chrome 133에서 실제 APK 선택→읽기 동의→기기 내 검사→별도 분석 동의→저장→JSON 다운로드→동일 자산 재검증을 확인했다. 파일 변경·동의 취소 시 읽기 동의 초기화, PC 동일 계정 조회 및 타 계정 거절도 확인했다. 실제 APK A 결과는 독립 SDK 근거와 일치하며 자산 1개·실행 2개로 저장됐다. 실물 기기·AAB/APKS/XAPK 실파일·설치/런타임은 별도다. [실제 Android 검증](validation/2026-10-30-android/README.md), [도구 보안·지원 정책](ANDROID_TOOLCHAIN_SECURITY_2026-10-30.md). 2단계 전체 완료는 아니다.


> **2026-10-30 Mac DMG 상태 갱신:** 담당자가 실제 Mac에서 DMG 검사를 다시 실행해 성공했다고 회신했고 사이트 결과 화면도 전달했다. 이전 DMG 실행 중단 문제는 **해당 파일·환경의 재시험에서 해소 확인(담당자 실검증)**으로 변경한다. 아래 과거의 DMG 재실행 대기 문구는 당시 기록이다. 캡처의 제작자 서명·Gatekeeper·추가 실행 보호·디버깅 접근은 unknown/미확인으로 유지한다. 실행 문제 해소와 보안 항목 충족은 별개다. 원본 JSON·도구 버전·해시를 독립 대조하지 않아 이전 실패의 정확한 원인이나 모든 DMG 호환까지 확정하지 않는다. PKG 실기기·Android·운영 DB/복구 등 잔여 작업 및 2단계 진행 중 상태는 유지한다. 캡처·개인 경로는 Git에 추가하지 않는다.


2026-10-29 작성. 이 문서는 **앞으로 실행할 검증 계획**이다. 아래 기간 관찰·복원·플랫폼 검사를 이미 완료했다는 뜻이 아니다. 모든 미래 장애나 취약점이 없음을 보장할 수는 없으며, 대상 버전·시나리오·증거를 고정한 범위에서 완료를 판단한다.

최신 수행 상태·전체 잔여 목록은 [2026-10-29 인계](PROGRESS_HANDOFF_2026-10-29.md)를 우선한다. Windows 내보내기 실행·Kali 조건별 출력/별도 격리 인증의 이미 확인한 범위를 반복 미완료로 계산하지 않는다. Android는 다른 PC의 다음 우선 작업, Mac은.4 재실행 회신 대기이며 아래 장기 운영/복원 완료 기준은 계속 남아 있다.

## 1. 간헐 DB 오류와 장기 안정성

- 먼저 코드 SHA·배포 ID·Node/DB/드라이버 버전과 쿼리 제한·읽기 복구 설정을 기록한다. 실제 회원의 페이지 이동→인증→진단→저장→조회→같은 자산 재검증까지 확인한다. health/ready 성공만으로 대신하지 않는다.
- 따뜻한 연결뿐 아니라 1/5/15/60분과 장시간 휴면 뒤 첫 요청을 구분한다. 제안 관찰 기간은 최소 72시간, 가능하면 7일이다. 승인된 작은 빈도로 운영을 관찰하고 동시에 격리 환경에서 동시 사용자 수·지연·연결 끊김을 시험한다. 실제 고객에게 대량 트래픽이나 운영 장애를 발생시키지 않는다.
- 경로·응답 코드·준비 상태 단계·고정 오류 사유·요청 ID·시각·p50/p95/p99 지연과 제한 시간 뒤 실제 완료를 대조한다. 비밀·SQL 값·원본 IP·쿠키는 수집하지 않는다.
- 원래 쓰기가 중복되지 않고, 실패 시 차단 확인을 생략하지 않으며, 다음 정상 요청에서 회복되는지 확인한다. 정상 사용 중 PROTECTION_UNAVAILABLE·저장 누락·교차 계정 노출이 발견되면 완료를 보류한다. 의도한 장애 주입 결과는 정상 운영 가용성 지표와 분리한다.
- 완료 증거: 정한 관찰 기간의 결과, 휴면/동시성 행렬, 실패 원인과 재검증, 저장/감사 건수 일치. 관찰 기간과 지연 목표는 운영 목적에 맞춰 합의한다.

## 2. 운영 백업 복구

1. 제공자 콘솔에서 **현재 요금제의 실제 백업 유무·시각·보존 기간**을 확인한다. 기능이 있다고 추정하지 않는다. Prisma 공식 문서상 자동 스냅샷은 특정 유료 플랜 대상이며 PITR 제공 시점도 별도다.
2. 필요한 pg_dump/pg_restore/psql을 공식 배포본에서 준비한다. Prisma의 해당 백업 안내가 요구하는 도구 버전을 맞춘다. 현재 PC의 최소 PG 실행 도구에는 pg_dump/psql이 없었다.
3. 먼저 스키마-only 복원, 이후 별도 승인·암호화·접근 통제 하에 필요한 데이터 포함 백업을 검증한다. 비밀은 명령 인수·채팅·Git에 넣지 않는다. 백업은 운영과 분리된 보관 위치와 키를 사용한다.
4. **운영 DB를 덮지 않고** 별도 DB/격리 VM으로 복원한다. 제공자 복원 자체를 검증하려면 제공자의 새 DB로 복원하는 경로도 시험해야 한다. 로컬 pg_restore 성공은 제공자 스냅샷 복구 성공과 다르다.
5. 테이블·함수·FK·행 수·비식별 체크섬·30일 보관 테이블·권한/기본 권한을 대조한다. 단순 dump 복원 옵션으로 생략한 ACL은 별도 재적용·검증한다. 전용 두 시험 계정으로 자기 기록 조회/타인 거절을 확인한다. 운영 사용자 비밀번호로 대신 로그인하지 않는다.
6. 허용 데이터 손실 시간(RPO)과 복구 시간(RTO)을 정하고, 실제 복원 시점과 복원 소요 시간이 목표 안인지 측정한다. 복원 환경의 세션·수집 키·외부 발송 연동은 운영에 재사용하지 않게 통제한다.

완료 증거: 읽을 수 있는 백업이 아니라 **실제로 복원된 별도 환경**과 무결성/접근 분리 결과, RPO/RTO 측정 기록. 백업 생성만 성공했다고 완료하지 않는다.

## 3. Linux 조건별 설정

- 소유한 Kali/Ubuntu VM에서 현재 OpenSSH 버전·실제 실행 서비스가 사용하는 설정 파일과 포함 파일을 확인한다.
- sshd -t로 문법을 확인하고 sshd -T로 기본 실효 값을 얻는다. sshd -T -C의 user/addr/host/laddr/lport 조건을 바꿔 실제 사용하는 계정·그룹·접속망의 Match/Include 조합을 대조한다. 결과를 출력하는 검사는 서비스를 재시작하지 않는다.
- 별도 검토 파일은 -f로 지정해 조건별 허용/거절 시나리오를 확인한다. 실제 로그인 성공/거절까지 확인할 때는 스냅샷과 복구 콘솔을 갖춘 격리 VM을 사용한다. 운영 SSH를 취약하게 변경하거나 복구 접속을 잃지 않는다.
- 사이트의 명시 값 5개와 실효 출력을 독립 비교한다. 원본 Include/Match가 들어오면 기존 미검사 표시를 유지한다. 유효 출력을 추린 파일은 원본 전체 설정과 구분해 표기한다.

완료 증거: 조건별 실효 출력, 예상/실제 결과, 원본/추린 사본의 구분, 사이트 저장/재검증과 계정 격리. 이전 사용자 제공 출력만으로 현재 VM·모든 조건을 완료하지 않는다.

## 4. Mac 고유 검증

- 실제 Mac 또는 이용 가능한 macOS 환경에서, 허가된 Mach-O/Universal/.app과 프로젝트 로컬 도구를 대조한다. Windows에서 만든 헤더 샘플로 macOS 신뢰 체계를 대신 검증하지 않는다.
- Apple 도구로 코드 서명 유효성·변조 여부·entitlement·Hardened Runtime을 확인하고, Gatekeeper/공증/스테이플 상태를 별도 대조한다. 단순 서명 존재와 신뢰 판단을 구분한다.
- 정상/서명 훼손/서명 없음/Universal 구조의 허가된 검토용 사본을 사용한다. 알려지지 않은 앱을 실행할 필요는 없다. 온라인 공증 조회와 오프라인 검증의 차이도 기록한다.
- 사이트가 실제로 지원하는 정적 관찰만 비교하고 미지원 항목을 임의로 pass로 바꾸지 않는다.

완료 증거: macOS·도구 버전, 동일 파일 해시, 플랫폼 도구/엔진/사이트 결과의 일치와 명시된 한계.

## 5. Android/iOS

- Android는 이 PC에 공식 SDK 도구와 AVD를 준비하면 물리 휴대폰 없이도 상당 부분 검증할 수 있다. apksigner와 Manifest 분석 결과를 사이트의 명시 설정과 대조한다. 현재 APK 서명 신뢰는 사이트 지원 범위 밖이므로 외부 도구 결과와 구분한다.
- 무해하고 허가된 시험 앱을 AVD에서 실행해 지원 Android 버전별 cleartext/네트워크 보안 설정·debuggable/backup 등 관련 동작을 확인한다. 설정을 생략했을 때의 OS/targetSdk 기본 동작을 사이트의 명시 값으로 오인하지 않는다.
- AAB/APKS/XAPK의 바깥 구조 검사가 내부 APK 전체·서명·실제 설치를 보증하지 않음을 확인한다.
- iOS Simulator는 Mac/Xcode가 필요하다. Info.plist/ATS 같은 지원 선언과 네트워크 동작을 비교할 수 있지만, 실제 기기의 서명·프로비저닝·설치·보호 기능을 전부 대신하지 못한다. 이 범위를 완료하려면 허가된 실제 iPhone과 적절히 서명된 앱도 필요하다.
- 두 일반 계정으로 PC/가상기기/실기기의 자기 기록 조회·다른 계정 거절, 파일 미선택·최대 1개·동의 취소·잘못된 형식·저장/재검증을 확인한다.

## 파일·화면 성능 변경의 별도 완료 기준

- 모든 파일 선택은 한 번에 최대 1개. 2개 이상이 전달되면 이전 선택/동의/결과를 지우고 오류를 표시하며 첫 파일만 몰래 처리하지 않는다. 서버는 배열/배치 필드를 거절한다. 파일 크기 제한은 모드별 기존 값을 유지한다.
- 화면 이동은 클릭 직후 이동 상태를 표시하고 loading 경계로 대기 화면을 제공한다. 내부 이동은 클라이언트 라우팅을 사용한다. 불필요한 모든 링크 선조회 대신 사용 의도가 있는 링크를 준비한다.
- 초기 목록→상세의 2회 요청을 초기 결과 1회 요청으로 줄이되 계정·카테고리·30일 필터·명시 ID의 소유자 검사를 유지한다. 격리 API 통합과 느린 응답 브라우저에서 로딩 표시를 별도 확인한다.
- 로딩 표시 시간, 실제 화면 도착 시간, 결과 준비 시간을 각각 측정한다. 로딩 UI를 빨리 보이게 한 것만으로 DB 응답이 빨라졌다고 쓰지 않는다.
