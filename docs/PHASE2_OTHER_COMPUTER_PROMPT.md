## 환경 확인과 실행 원칙

설치돼 있는 OS·Node·패키지·PostgreSQL 도구·VMware·GNS3·Android/iOS/macOS 도구와 접근 가능 대상만 확인하세요. 환경이 없는 대상을 임의 설치하거나 완료라고 하지 말고 보류로 기록하세요. 실제 비밀번호·SSH 개인키·API 키를 채팅이나 스크린샷으로 요구/노출하지 마세요. 기존 로그인은 사용자가 직접 입력할 수 있게 하세요. 자체 테스트 서버/DB가 필요하면 사용자 DB와 분리된 loopback 임시 환경을 사용하고 외부에 열지 마세요.

일반 회원(viewer 포함)도 본인의 허가된 자산을 점검합니다. 관리자 승격이나 다른 계정 데이터 접근을 허용하지 마세요. 설정 원본을 결과·Git·AI·보고서에 복사하지 말고 고정된 관찰값·도구 버전·익명화된 근거만 남기세요. 안전을 보증하거나 미검사를 통과로 바꾸지 마세요.

## A. 다른 컴퓨터 Linux — 우선 진행

1. 소유하거나 명시적 허가를 받은 Linux의 배포판·OpenSSH 버전·검증 시각을 기록합니다. 로컬 콘솔 또는 이미 허용된 읽기 경로를 우선하고 root/SSH 접근을 새로 열지 마세요.
2. 권한이 허용하면 `sshd -t`와 `sshd -T`의 결과를 확인합니다. Match 조건이 있다면 실제 사용자의 조건으로 `sshd -T -C user=...,host=...,addr=...`도 비교합니다. 이 명령은 설정 검증/출력이며 서비스를 재시작하지 않습니다. 실제 실행 경로·sudo 권한은 환경에서 확인하세요. 접근이 막히면 우회하지 말고 이유를 기록하세요.
3. 원본 Include/Match 설정을 사이트에 넣었을 때 미검사로 처리하는지, 기본값을 추측하지 않는지 확인합니다. 운영 설정을 삭제/단순화해서 통과시키지 마세요.
4. 별도로 유효 출력의 지원되는 다섯 지시어만 추린 **검토용 사본**과 비교합니다: PermitRootLogin, PasswordAuthentication, PermitEmptyPasswords, PubkeyAuthentication, MaxAuthTries. 원본 파일 검사와 유효 출력 검사를 서로 다른 근거로 표시하세요.
5. 취약/보완 더미 파일로 같은 자산 이름의 전후 비교 5개 개선을 확인하되 실제 sshd 설정을 취약하게 변경하거나 재시작하지 마세요. 정식 사이트에 다른 컴퓨터에서 로그인→진단→저장→조회/재검증까지 확인합니다. 이 PC에서 만든 결과가 다른 기기 같은 계정에 보이고 별도 계정에는 안 보이는지도 테스트 계정으로 확인합니다.

## B. VMware·GNS3 — 설치된 경우만

- VMware: 제품/버전·검토용 VMX 사본을 기록하고 명시적 격리/VNC/NIC 값만 대조합니다. NAT/Host-only를 완전 격리라고 하지 마세요. 실행 중인 VM 설정을 직접 변경하지 마세요.
- GNS3: 실제 설치 버전과 저장한 `.gns3` 내부 version을 기록합니다. 현재 지원 선언은 **2.x JSON 구조**이며 3.x/알 수 없는 버전은 거절해야 합니다. 2.x 한 버전의 확인으로 모든 2.x 제품 호환을 인증하지 마세요.
- Cloud/NAT와 콘솔 바인딩의 선언을 결과와 대조합니다. 장비 ACL·암호·실제 Telnet 서비스는 파일만으로 알 수 없으므로 미검사로 유지합니다.
- 실제 통신은 이미 격리된 승인 실습망에서만 최소 ping/허용·차단 관찰로 확인합니다. VM/프로젝트 실행이나 장비 변경은 기존 허가 범위를 확인한 후 진행하고 외부망을 스캔하지 마세요. 장비 OS·템플릿·이미지 라이선스가 없으면 만들거나 다운로드하지 말고 보류하세요.

## C. 실제 Windows·Mac·모바일 — 가능한 대상만

- Windows: 승인된 PE 파일과 읽기 전용 정책 내보내기를 검사합니다. 정책 JSON은 GPO·예외를 포함한 현재 실효 정책 전체의 증명이 아닙니다. OS 서명 도구와 앱 결과를 대조하고 unknown을 임의 수정하지 마세요.
- Mac: Mac이 있을 때만 Mach-O/Universal 파일과 프로젝트 로컬 도구의 실제 사용법·동의 요구를 읽고 실행합니다. codesign/Gatekeeper/Hardened Runtime/entitlement의 지원 관찰을 대조합니다. Mac이 없으면 브라우저 Mach-O 합성 분석만 완료, OS 서명 검증은 보류로 유지하세요. 샘플 실행/설치를 요구하지 않습니다.
- Android/iOS: 허가된 APK/IPA의 명시적 설정을 기존 플랫폼 분석 도구 출력과 대조합니다. AAB/APKS/XAPK는 구조 관찰이며 중첩 앱·protobuf 전체 설정·서명·설치/런타임을 검사했다고 쓰지 마세요. 실제 기기/에뮬레이터가 없으면 정적 파일 점검과 실기기 확인을 구분합니다. 위험한 앱을 기기에 설치하지 마세요.
- 모든 파일: 선택만으로 읽지 않음→읽기 허용→부분 검사→소유/진단 동의→요약 저장을 확인합니다. 파일 변경/취소 시 동의와 요약이 초기화되는지, 미검사 항목이 보완 후에도 남는지 확인합니다.

## D. R01~R07 후속 및 검토

- R01: 운영 오류 발생 시 UTC/한국 시각·경로·상태·Vercel 요청 ID를 즉시 기록하고 보존 기간 안에 runtime 로그와 DB 지표를 대조하세요. 2026-10-26 23:59:34 UTC `/signup` 503 뒤 10/27 00:32 UTC 200을 요청 로그로 확인했습니다. Hobby의 과거 runtime 보존 한계로 원인은 미확정입니다. 보호를 꺼서 성공시키지 마세요. 준비 상태 성공은 로그인/실제 진단 성공을 대신하지 않습니다.
- R02: 관리형 DB 자격의 실제 권한·비밀 유출 영향·백업 복구 경계는 미완료입니다. 앱 SQL 차단 검사가 탈취된 DB 자격까지 보호하지는 않습니다. 운영 키 폐기/DB 복원은 별도 승인·준비 없이 실행하지 마세요.
- R03/R04: 요청별 스크립트 nonce와 MUI/Worker/로그인/파일 검사 호환, 출처+계정별 한도를 확인하세요. style unsafe-inline은 남아 있습니다. 공유 NAT 사용자 영향과 글로벌 예산은 잔여 제한입니다. 운영 대량 요청으로 시험하지 마세요.
- R05/R07: GNS3 2.x 형식 게이트와 등록 모듈/DB CHECK readiness 검사를 확인하세요. 적용된 migration을 편집하지 말고 필요하면 새 migration을 작성합니다.
- R06: 실제 확인 결과에 맞춰 prompt/PHASE2/PROJECT_STATUS/README와 검토 보고서의 날짜·범위·미검증을 일치시키세요.
