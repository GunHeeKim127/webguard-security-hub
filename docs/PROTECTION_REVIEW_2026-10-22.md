## 수정

일반 쿼리의 제한을 그대로 두고 **정확한 IP 차단 SELECT 하나에만** Prisma 클라이언트 대기를 5초에서 10초로 조정했다. 접속 권한을 바꾸거나 DB 검사를 생략하지 않는다. 오류가 난 클라이언트는 폐기하며 읽기만 기존 정책대로 1회 재시도한다. 차단 기록 쓰기와 다른 SELECT에는 새 제한을 적용하지 않는다.

보호 DB 조회를 명시적인 풀 checkout/release로 실행해 연결 대기와 실제 쿼리를 나눠 진단한다. 로그는 단계·시간·고정 오류 종류만 포함하고 값·SQL·오류 원문은 포함하지 않는다. 변경으로 제공자 장애 자체가 해결됐다고 주장하지 않는다.

## 재현 및 검증

- 100개 단위/회귀 테스트와 TypeScript 검사 통과. 정확한 조회에만 제한 적용, 일반 PostgreSQL/다른 SELECT/쓰기의 제한 유지, 실패 연결 폐기·재실행 없음·로그 비밀 비노출을 확인했다.
- 별도 임시 PostgreSQL의 `ip_blocks`를 6초 잠가 동일 SELECT를 지연시켰다. 기존 5초 클라이언트는 `Query read timeout`, 수정된 보호 조회는 약 6초 뒤 실제 DB 결과를 반환했다. 운영 DB에는 잠금·시험 기록을 만들지 않았다.
- production 빌드와 전체 HTTP/DB 통합 검증 통과. 계정/세션 격리·CSRF/SSRF·IP 차단/해제·실패 보존·재검증 이력·관리자 복구·Prisma SQL 프로필도 통과했다. Git 배포 후 운영 점검은 실행 결과를 별도로 확인한다.

운영 환경 설정·자격증명·CLI·시험 데이터는 Git 제외 work/에만 보관한다. 제품에 테스트 파일이나 시험 계정을 추가하지 않는다.
