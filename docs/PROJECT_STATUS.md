# WebGuard Security Hub — 기획 대비 구현 현황

작성일: 2026-10-16 (한국 시간)

현재 상태는 **단일 조직에서 로컬로 실행하고 검증할 수 있는 보안 헤더 진단·운영 현황 MVP**입니다. 여러 외부 사이트를 실시간으로 보호하는 통합 보안 서비스 단계에는 아직 도달하지 않았습니다. 단순 화면 시제품은 넘었지만, 외부 고객에게 바로 공개할 운영 제품은 아닙니다.

## 비교 기준과 원문 접근 범위

이전 「보안 프로젝트 기획」 대화에서 확인한 사용자 요구는 다음과 같습니다.

1. 모든 것을 한곳에서 확인하는 사이트.
2. 보안 서비스를 제공하는 사이트 자체의 보안 강화.
3. 이상한 접근·악용 트래픽을 감지하고 봇/AI로 의심되는 접근을 걸러 더미 사이트로 분리.
4. PostgreSQL을 DBeaver로 관리하고 프로젝트 폴더 안에서 SQL migration 관리.
5. 비밀 탈취를 막고 AI를 API로 연결해 관리에 활용.

대화 조회에는 위 사용자 메시지와 후속 저장 경로 요청이 포함되어 있습니다. 과거 assistant 답변은 본문 대신 참조 표시만 반환되어, 당시 답변의 상세 설계까지 모두 복원한 것은 아닙니다. 이 문서는 확인 가능한 사용자 요구, 현재 대화의 후속 요청, 실제 소스 및 실행 검증을 기준으로 분석했습니다.

## 구현 근거

- `app/api/scans/route.ts`, `lib/scanner.ts`, `lib/scan-store.ts`: 진단·SSRF 방어·최신 결과 저장.
- `app/home-client.tsx`, `app/operations-panel.tsx`, `lib/scan-run.ts`: 화면 흐름·실제 진행 이벤트·로그 다운로드.
- `app/api/register/route.ts`, `app/api/login/route.ts`, `lib/security.ts`, `lib/password.ts`: 계정·세션·권한.
- `sql/setup/`, `sql/migrations/`, `scripts/migrate.ts`, `scripts/grant-runtime.ts`: DB 분리와 migration.
- `app/api/ai/route.ts`, `lib/ai-providers.ts`, `lib/ai-chain.ts`, `lib/ai-budget.ts`, `lib/advice-cache.ts`: AI 자동 전환·한도·답변 재사용.
- `lib/traffic.ts`, `app/[...probe]/route.ts`, `app/decoy/route.ts`: 허브 내부 접근 이벤트와 최소 디코이.
- `lib/request-locale.ts`, `lib/geo-country.ts`: 언어 우선순위와 신뢰된 국가 힌트.

Prisma는 현재 필수 의존성이 아닙니다. DB는 pg와 프로젝트 내 SQL migration으로 관리합니다. DBeaver는 조회·관리 도구이며 앱의 DB 연결 경로와 구분됩니다.

## 현재까지 검증한 것

- 보안·언어·진행 스트림·기본 안내·AI 전환 관련 자동 테스트 34개.
- TypeScript 검사와 프로덕션 Webpack 빌드.
- 임시 PostgreSQL의 DB 분리·최소 권한·회원가입·로그인·세션·중복 결과 갱신·동시 저장·캐시·실패 한도 반환·디코이 이벤트.
- 로컬 가짜 AI 제공자로 실제 HTTP API의 성공·토큰 수·캐시 재사용·한도 오류 시 기본 안내 전환.
- 실제 소유 사이트의 HTTP 200 헤더 진단, 단계별 로그·다운로드·주소 변경 초기화.
- 실제 Groq `openai/gpt-oss-120b`, Gemini `gemini-3.5-flash-lite`의 한국어 응답 각 1회 및 브라우저의 저장 답변 재사용.

모든 공격에 안전하다는 보장, 외부 보안 감사, 실제 부하 시험 또는 24시간 운영 검증을 수행한 것은 아닙니다. 상세 이력은 `VALIDATION.md`를 참고하세요.

## 공개 전에 우선 해결할 항목

1. **가입과 데이터 범위:** 현재 신규 viewer도 허브 전체 진단 결과를 볼 수 있는 단일 조직 구조입니다. 공개 서비스로 바꾸려면 가입 승인 또는 초대제, 조직/사용자별 데이터 분리, 자산 소유·진단 허가 관리가 먼저 필요합니다. DB를 프로젝트별로 나눈 것과 웹 회원별 접근 분리는 별개입니다.
2. **운영 비밀·배포:** 실제 환경 파일은 Git에서 제외하되 OneDrive 동기화 대상은 별도 관리해야 합니다. 운영에서는 비밀 저장소, HTTPS/HSTS, 외부 DB TLS, egress 제한과 백업 복원 검증을 적용해야 합니다.
3. **계정 복구·강화:** 이메일 인증, 비밀번호 찾기, MFA/SSO와 관리자 권한 변경 경로를 추가해야 합니다.
4. **운영 관측:** 접근/오류 로그 보존, 알림, 장애 대응, 의존성 패치 및 만료 데이터 정리 스케줄을 마련해야 합니다.

## 원래 기획으로 확장할 다음 순서

1. 조직·프로젝트·자산 등록과 권한 모델을 먼저 완성합니다.
2. 보호할 사이트에 리버스 프록시/수집기를 연결하고 실제 접근 로그를 수집합니다.
3. 요청 제한·의심 경로·인증 공격 등 설명 가능한 탐지 규칙과 수동 검토 화면을 만듭니다.
4. 차단·격리·허용 정책과 정상 사용자 구제 수단을 검증한 뒤 분리된 디코이로의 정책 기반 이동을 추가합니다. 봇/AI 여부만으로 자동 처벌하지 않습니다.
5. AI는 수집된 안전한 요약을 설명하는 데 사용하고, 실제 정책/DB 변경은 승인·테스트·롤백 체계 뒤에 둡니다.

## Git 정리 범위

원격은 `GunHeeKim127/webguard-security-hub`, 기본 브랜치는 main입니다. 기존 원격 첫 커밋에 포함된 임시 PostgreSQL 테스트 파일 998개는 최신 버전의 추적에서 제외합니다. 로컬 테스트 파일과 기존 커밋 이력은 보존합니다. 따라서 과거 커밋에는 해당 테스트 파일이 남습니다. 실제 환경 파일은 업로드 대상에서 제외하며, 비밀 값 대조 검사는 값 자체를 출력하지 않고 수행합니다. 이는 모든 종류의 비밀 유출 가능성을 보장하는 감사는 아닙니다.
